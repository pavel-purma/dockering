# Feature: Distribution, releases & cross-platform updates

- **Status:** in-progress (existing release flow); **shared updater implemented (plan approved 2026-10-19, built 2026-10-20) and verified on Linux, still `in-progress` for what is open: the Windows behaviour (spike W1), the maintainer's update keys and the first updater release; see the verification table and the plan's open items:** one shared updater on Windows, macOS and Linux (discovery, notification, title-bar button, Settings, retained offer), installing without OS code signing through the Inno installer (Windows) and an in-place AppImage swap (Linux); macOS offers *Download* and its in-app install is deferred (UPD-013…017, REL-083…087). Prior release verification below is historical, not proof of the revised updater. Windows installer behaviour beyond the existing smoke tests is unverified (spike W1); winget and release-bot activation remain deferred.
- **Requirement prefixes:** REL (release, packaging, signing, winget, branding, Linux smoke test; REL-001…003 licensing stay in [spec 50](../50-build-and-release.md#licensing-rel-001)) · UPD (in-app updates)
- **Plan:** [windows-distribution](../../plan/features/windows-distribution.md) · [linux-install-smoke-test](../../plan/features/linux-install-smoke-test.md) (§8) · [cross-platform updates](../../plan/features/linux-appimage-updates.md) (stable slug retained; UPD-013…017, REL-083…087) · **ADR:** [0007](../../plan/adr/0007-cross-platform-updater.md) (accepted)

Dockering ships through **GitHub Releases** (the only storage for binaries), a branded **Inno Setup**
installer on Windows, **winget**, and an opt-out **in-app updater** that reads a signed manifest
from the latest GitHub Release. Discovery, schedule, trust, opt-outs, notifications, indicator,
retained offers and Settings MUST be shared on Windows, macOS and Linux. Only installation
strategy differs: the Inno installer (Windows) and an in-place AppImage swap (Linux) install the
update, with no OS code signing needed; every other install, macOS included, gets a truthful
*Download* fallback, never a claim of installed success.

The repository is public. The first release, [v0.1.0](https://github.com/pavel-purma/dockering/releases/tag/v0.1.0),
and the second, [v0.2.0](https://github.com/pavel-purma/dockering/releases/tag/v0.2.0), were published as
explicitly **unsigned** releases (REL-016), with signing, notarization,
the updater, winget, and release-bot setup deferred. Public visibility alone
does not enable those features. See [the first-release plan](../../plan/features/unsigned-first-release.md).
Releases are cut with the `/release` skill (REL-018). They stay unsigned until a signing provider is set up; the
pipeline keeps the hooks for it: [plan](../../plan/features/release-skill-and-signing.md), [signing guide](../../signing.md).

## 1. Release flow (REL-010…019)

| ID | Requirement |
|---|---|
| REL-010 | **Release flow.** Trunk-based on `main`, squash merges, and conventional-commit PR titles (enforced by a required PR-title check (REL-080)). A release is cut with the `/release` skill (REL-018), which prepares **one release PR** `chore(release): vX.Y.Z`: it bumps `[workspace.package] version` and `Cargo.lock` and adds the changelog sections (REL-011, REL-019). The steps are: (1) after the maintainer approves the version and the changelog, the skill opens the PR, waits for every check, and squash-merges it; (2) it pushes the annotated tag `vX.Y.Z` on the merge commit, which starts `release.yml`; (3) `release.yml` builds, signs, and uploads every asset to a **draft** GitHub Release, with notes from that `CHANGELOG.md` section; (4) the skill verifies the draft (REL-018) and, after the maintainer approves, publishes it. Publishing is the only step that makes a version visible to users, the updater (UPD-001), and winget (REL-041). The workflow never publishes. **Pre-releases** (`-alpha.N`, `-beta.N`, `-rc.N`): the maintainer passes the version (`/release 0.3.0-rc.1`). They become GitHub *pre-releases* and are never "latest". **Hotfixes:** fix on `main` and release a patch. If `main` has unreleasable work, branch `release/X.Y` from the tag, cherry-pick, and release by hand (the skill works from `main`); the tag check accepts `release/*`. **Manual fallback:** the maintainer can bump, tag and push by hand ([release.md](../../release.md)); `release.yml` checks it the same way. release-plz (`release-plz.yml`, `release-plz.toml`) stays dormant without its bot secrets and MUST NOT be enabled alongside the skill, because both open release PRs. A branch `workflow_dispatch` MUST build and assemble a complete review artifact without creating a tag or release; dispatch on an existing version tag follows the draft-release path. |
| REL-011 | **Versioning and changelog follow the commits.** `cargo xtask release-plan` lists the conventional commits since the last stable `v*` tag and computes the next version; the `/release` skill writes the changelog sections (REL-019). All workspace crates share the workspace version, so a `feat:` in any crate bumps the app; `xtask` is never released. Bumps: a breaking change → minor while `0.x` (major from `1.0`; leaving `0.x` is always the maintainer's explicit choice); `feat` → minor; `fix`, `perf`, `refactor`, `revert` and other user-visible commits → patch. `docs`, `test`, `chore`, `ci`, `style` and `build` commits, and commits scoped `ci`, `release`, `docs`, `spec` or `deps`, don't count (unless breaking). `CHANGELOG.md` keeps the Keep a Changelog shape (*Added*, *Changed*, *Deprecated*, *Removed*, *Fixed*, *Security*) with one user-facing entry per visible change rather than one per commit; the bump that the written sections imply must equal the computed one. `release.yml` fails if the tag ≠ workspace version or if `CHANGELOG.md` has no section for the version, and `cargo xtask release-verify` runs the same checks before anything is pushed. |
| REL-012 | **Stable asset names.** Every release uploads version-less names, so `https://github.com/pavel-purma/dockering/releases/latest/download/<name>` is a permanent download link. Windows: `Dockering-Setup-x64.exe`, `Dockering-Setup-arm64.exe`, `Dockering-x64.zip`, `Dockering-arm64.zip`. macOS: `Dockering-aarch64.dmg`, `Dockering-x86_64.dmg`. Linux: `Dockering-x86_64.AppImage`, `Dockering-aarch64.AppImage`, `Dockering-x86_64.deb`, `Dockering-aarch64.deb`, `Dockering-x86_64.tar.gz`, `Dockering-aarch64.tar.gz`. Plus `SHA256SUMS` (all assets), `dockering-update.json`, `RELEASE_NOTES.md`, and `dockering-update.json.minisig` when `sign_manifest` is true (REL-083; UPD-002/003). |
| REL-013 | **Supply chain.** Signing secrets MUST reach only the steps that use them. Public-repository releases and manual review bundles MUST carry GitHub build-provenance attestations independently of code signing. Private-repository attestations MAY be skipped where the GitHub plan does not support them. Signing jobs use the `release` environment. Workflows use least-privilege permissions; third-party release actions are pinned. Release-bot App setup is optional for the manual-tag flow. Publication remains an explicit maintainer action. |
| REL-014 | **CI builds the installer.** On pushes to `main`, CI builds the unsigned Windows installer for x64 and arm64 and uploads it as a workflow artifact. An `installer-smoke` job on `windows-2025` does the following: silent per-user install → `dockering.exe --version` from the install dir prints the workspace version → silent uninstall → the install dir and the uninstall registry key are gone. The same runs for `/ALLUSERS`. |
| REL-015 | **Project home page.** `README.md` starts with the app icon, name, and one-line tagline. Then come badges, a screenshot, *Download* links per OS/arch (REL-012 stable links), install instructions (winget, installer, portable zip, build from source), the feature list, a *Privacy & network* section (what the updater contacts, how to turn it off; UPD-010), and links to the spec and contributing. Badges: CI (`ci.yml`) and Release (`release.yml`) workflow status now. Latest version, downloads, license, and winget version (shields.io) are added at the public launch, because shields.io can't read private repos. Repo *About*: description, topics, and the social-preview image (1280×640). Texts in [plan §A4](../../plan/features/windows-distribution.md#a4-home-page-copy). |

| ID | Requirement |
|---|---|
| REL-016 | **Explicit unsigned releases.** The maintainer MAY publish an unsigned stable or prerelease after approval. Dispatch `unsigned` defaults true; tags default unsigned while `PUBLIC_RELEASES` is not true. Unsigned mode MUST bypass OS code signing/notarization even if secrets exist, but MUST NOT override the independent cross-platform updater gate (REL-083). Updater-enabled unsigned binaries still require a signed manifest. Notes MUST disclose OS signature status and actual installation/fallback limitations. All tags create drafts; publication requires separate approval. |
| REL-017 | **Complete assets.** Before assembling a release or review bundle, the workflow MUST require all 12 distribution files named in REL-012, reject missing or empty files, and reject duplicate names while collecting matrix artifacts. Per-target packaging MUST validate its expected files before uploading. The bundle MUST include `dockering-update.json`, `SHA256SUMS`, and release notes; `.minisig` is included when `sign_manifest` is true (REL-083) and omitted otherwise. |
| REL-018 | **Release skill.** `/release` (`.agents/skills/release/`, shared by Claude Code and OpenCode) runs REL-010 end to end and resumes from whatever state it finds. Before it pushes anything it MUST write both changelogs (REL-019), choose the version (REL-011), and pass the local gate: formatting, clippy (also with the `updater` feature), the NFR-001 check, tests, `cargo deny`, the notices diff, a release build that prints the new version, and the host's package. It MUST stop for the maintainer's approval before the release PR is created and before the draft is published; `auto` skips a stop only when the channel is unchanged, nothing warned, and every check, including the launch check, passed. It verifies the draft with `scripts/verify-release.ps1` (file set, checksums, manifest, notes, executable properties and signatures, attestations, and a launch of the downloaded app on a profile written by the previous version, the check that would have caught the first 0.2.0 build) and the published URLs afterwards. It MUST NOT push to `main`, move or delete a tag, change a published release, run the installer smoke test on the maintainer's machine, or handle a secret value; a broken published build is the maintainer's decision. `cargo xtask release-plan`, `release-verify` and `verify-manifest` are its deterministic helpers; `/release status` and `/release signing` report state and guide the signing setup. |
| REL-019 | **Changelogs are written at release time.** The version sections of `CHANGELOG.md` and the lines of `docs/spec/CHANGELOG.md` are added only by the release skill, in the release PR, from the merged commits and their PR descriptions: a user-facing section per version, and one spec line per merged change under `docs/spec/**`. Feature, fix and docs PRs, and the `feature-planning` skill, MUST NOT add to either, because concurrent PRs conflict on their first lines. A PR that changes the spec says what changed in its description. |

## 2. Windows installer (REL-020…028)

| ID | Requirement |
|---|---|
| REL-020 | **Inno Setup 6** installer per architecture (x64, arm64), built from `packaging/windows/dockering.iss` by `cargo xtask package` (format `inno`). It replaces the WiX `.msi` (x64) and NSIS `.exe` (arm64) on Windows. cargo-packager stays for macOS and Linux. |
| REL-021 | **Install scope.** The default is per user without admin rights (`PrivilegesRequired=lowest`), into `%LocalAppData%\Programs\Dockering`. All-users install (`/ALLUSERS`, or the wizard's scope dialog) goes into `%ProgramFiles%\Dockering`. The `AppId` GUID is fixed forever. Installing a newer version upgrades in place; re-running the same version repairs. |
| REL-022 | **Wizard.** `WizardStyle=modern` with branded images generated from the app icon (REL-050). Minimal pages: scope (only when interactive), optional desktop shortcut (off by default), install progress, finish with *Launch Dockering* (on). No licence-acceptance page (permissive licences); the licence files are installed. The uninstaller asks whether to remove settings and logs (default: keep). Silent uninstall keeps them. It removes the data of the user running the uninstaller only; for an all-users install run by an admin, that is the admin's profile. |
| REL-023 | **Shell integration.** Start Menu shortcut *Dockering* with AppUserModelID `dev.dockering.Dockering`. The app sets the same AUMID at startup, so taskbar pinning and grouping match. An *Installed apps* entry with icon, publisher, version, and help/update URLs (GitHub). Installs `LICENSE` (MIT, REL-001) and `THIRD_PARTY_LICENSES.html` (REL-002). |
| REL-024 | **Running app.** The app holds a named mutex `dev.dockering.Dockering` for its lifetime, next to the SHL-022 single-instance pipe. The installer uses it as `AppMutex` and closes a running Dockering via the Restart Manager (`CloseApplications=force`). Interactive installs ask first. Silent installs close it. |
| REL-025 | **Silent mode** (winget, updater, CI): `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /SP-` exits 0 without UI. Silent uninstall leaves no files in the install dir and no *Installed apps* entry. |
| REL-026 | **Portable zip** (`Dockering-<arch>.zip`): `dockering.exe` plus licence files. It runs without installation and is detected as *portable* (UPD-006). |
| REL-027 | **Executable resources.** `dockering.exe` embeds the app icon as icon resource **ID 1** (GPUI's Windows backend loads resource 1 as the window and taskbar icon) and a `VERSIONINFO`: `ProductName`/`FileDescription` "Dockering", `CompanyName`, `LegalCopyright`, `OriginalFilename`, and `FileVersion`/`ProductVersion` from the workspace version. |
| REL-028 | **No console window.** Release builds of `dockering.exe` on Windows MUST be GUI-subsystem executables (`windows_subsystem = "windows"` when `debug_assertions` is off), so starting the app from Explorer, the Start Menu, a shortcut, or the installer's *Launch Dockering* opens only the app window. Debug builds stay console executables, where `cargo run` shows the log (10 §8). Output meant for a terminal (`--version`, startup errors) attaches to the launching terminal's console on demand (`dk_hub::console`); with no terminal it is dropped, and a missing or closed stdout/stderr never panics. A GUI process has no console to inherit, so every console program the app runs in the background (`wsl.exe`, `wslc.exe`, Docker credential helpers) MUST set `CREATE_NO_WINDOW`, or it would open its own window. Two launches are exempt: the external terminal (TRM-009, its window is the point) and the installer the updater starts detached (UPD-007, a GUI program). A shell doesn't wait for a GUI-subsystem program, so `$v = dockering --version` captures nothing in PowerShell; `dockering --version | Out-String`, `cmd /c`, and `Start-Process -Wait -RedirectStandardOutput` work. `installer-smoke.ps1` asserts that the installed `dockering.exe` has the GUI subsystem. |

## 3. Code signing (REL-030…034)

| ID | Requirement |
|---|---|
| REL-030 | Every Windows executable in the **signed stable channel** (`PUBLIC_RELEASES=true`, without the explicit unsigned override in REL-016) MUST be Authenticode-signed with SHA-256 and an RFC 3161 timestamp. The explicitly requested unsigned release mode is exempt. Signing runs only in CI; keys and tokens never enter the repo or logs (NFR-020). Signing the Inno-generated uninstaller remains a tracked limitation of remote providers. |
| REL-031 | **Pluggable provider.** `WINDOWS_SIGNING` selects `azure` or `none` (default `none`); more providers MAY be added as the same kind of step. Signed stable releases MUST fail without verified Windows signatures and the update signing key. Unsigned mode (REL-016) MUST skip every OS code-signing and notarization step even if provider variables or secrets exist (the manifest signature of REL-083 is not OS signing), and MAY produce a stable draft for explicit publication. Signing order remains binary before packaging, then installer. Signed mode also requires a public key in `crates/dk-update/src/keys.rs`, so a signed build can verify the manifest it ships (UPD-003); macOS signing doesn't gate the signed channel (REL-034). Setup and operation: [signing.md](../../signing.md). |
| REL-032 | CI checks every signed file (`Get-AuthenticodeSignature` = `Valid`, an RFC 3161 timestamp, a SHA-256 digest, one signer across files, and that signer = repo variable `WINDOWS_SIGNER_SUBJECT`, which a signed tag build REQUIRES) and fails the job on any mismatch. Whenever `sign_manifest` is true (REL-083), the run also fails without `UPDATE_SIGNING_KEY` or a compiled-in public key, and the signed manifest is checked against those keys before the draft is created (`cargo xtask verify-manifest`, REL-084); only the Authenticode checks are exempt in unsigned mode (REL-016). |
| ~~REL-033~~ | ~~**Code signing policy.** The README *Code signing policy* section and the signed notes' policy link and provider attribution.~~ (removed 2026-10-20: it existed only for the provider that was not adopted; the release notes and the README no longer carry it.) |
| REL-034 | **Per-platform signing.** Windows and macOS signing are independent. `WINDOWS_SIGNING` selects the Windows provider (REL-031); `MACOS_SIGNING` is `apple` or `none` (default `none`). With `apple`, a signed release requires the Apple secrets, signs the `.app` and notarises and staples the DMGs. With `none`, macOS files are built unsigned even in the signed channel and the release notes say so. A signed release never requires macOS signing. |

## 7. In-app updates (UPD-001…017)

UPD-013, UPD-014, UPD-015 and UPD-017 are new and UPD-003 and UPD-005…UPD-012 were revised with the [plan](../../plan/features/linux-appimage-updates.md); all of it is implemented and verified on Linux (2026-10-20), see the Verification table. What no one has run yet: the Windows behaviour beyond the CI update leg (spike W1, REL-087) and a real release with `UPDATER=all`. macOS in-app install is deferred (UPD-016).

| ID | Requirement |
|---|---|
| UPD-001 | **Source = GitHub Releases only.** The app fetches `https://github.com/pavel-purma/dockering/releases/latest/download/dockering-update.json` and its `.minisig`. Every asset URL in the manifest must be `https://github.com/pavel-purma/dockering/releases/download/v<that version>/<plain file name>`; anything else is rejected. GitHub serves *latest* = the newest published non-pre-release, so drafts and pre-releases are never offered. No REST API calls are made, so there is no rate limit. A *Preview* channel (pre-releases) MAY be added later through the Releases API. |
| UPD-002 | **Manifest** (JSON, `schema: 1`): `version`, `pub_date`, `notes_url`, and `platforms` keyed `<os>-<arch>` (`windows-x86_64`, `windows-aarch64`, `macos-aarch64`, …) → `{ kind: inno|zip|dmg|appimage|deb|tar.gz, url, sha256, size }`. `release.yml` generates it from the built assets with `cargo xtask update-manifest`. Unknown fields are ignored; an unknown `schema` means "no update". |
| UPD-003 | **Integrity.** The manifest must carry a valid **minisign** (Ed25519) signature from a public key compiled into the app (current + next). The private key is the secret `UPDATE_SIGNING_KEY` in the `release` environment. Any manifest without a valid signature is rejected. A downloaded file must match `size` and `sha256` before use. On Windows, when the running `dockering.exe` is Authenticode-signed, the installer must also have a valid signature whose signer (full subject DN **and** issuer DN) matches the running exe's (`WinVerifyTrust`); a running exe whose own signature doesn't verify fails closed. Otherwise the installer is deleted and never run. Size, SHA-256 and the signature are checked again right before *Restart to update* starts it. **Unsigned installs run on the same trust.** With an unsigned running exe (an unsigned release) a Windows installer is accepted on the signed manifest, size and SHA-256 alone; an AppImage carries no code signature on any distribution, so the manifest signature is the only trust root there too, and the payload is checked again before staging and hashed while the staged copy is written, and the staged file must pass the `--version` self-test before it replaces anything (UPD-014). A signed running exe never accepts an unsigned installer: the offer degrades to *Download* with the reason in Settings (UPD-017). 'No signature' means no certificate table; any other failure to read or verify a signature counts as invalid and fails closed. |
| UPD-004 | **Schedule.** When enabled: first check 30 s after startup, then every 24 h (± 1 h jitter) while the app runs. *Check for updates* runs one now. Only a strictly greater SemVer is offered (no downgrades; a pre-release is never offered to a stable build). Errors on automatic checks are logged and retried next cycle. Only a manual check shows them. |
| UPD-005 | **Shared opt-out & build gate.** Cargo `updater` is off by default; release inclusion is solely `UPDATER=none|all` (REL-083), independent of OS signing. Missing/invalid trust keys MUST fail closed before network access. Dev/debug, demo, builds without the feature, `DOCKERING_DISABLE_UPDATES=1`, and applicable administrator policy disable check/download/apply including manual checks, with zero updater requests. Windows policy remains `HKLM` or `HKCU\Software\Policies\Dockering\DisableUpdates` = 1; no new macOS/Linux policy store is assumed. Only the Settings automatic-check opt-out permits *Check now* and explicit use of a retained offer; it stops automatic checks/downloads, not explicit actions. |
| UPD-006 | **Install strategy only.** Discovery, notification, the title-bar button and Settings never depend on the install kind or on OS code signing. The strategy decides only what *Restart to update* does: Inno per-user and per-machine (UPD-007) and a writable Linux AppImage (UPD-013, UPD-014) install the update. Everything else offers *Download* (opens the release page): the Windows portable zip, `.deb`, `.tar.gz` and other package-managed or read-only Linux installs, an AppImage in a read-only place, and **every macOS install** (in-app macOS installation is deferred, UPD-016). A *Download* offer starts no asset download and never reports an installed update. Eligibility is probed again on a blocking hub worker at every check and at apply; a lost eligibility downgrades the offer to *Download* instead of removing it. |
| UPD-007 | **Apply (Windows).** Only an explicit *Restart to update* starts the verified Inno installer, detached, with argv `/SILENT /SUPPRESSMSGBOXES /NORESTART /SP- /UPDATE /RELAUNCH` plus `/CURRENTUSER` or `/ALLUSERS` (no shell, NFR-022). Per-user: a detached child. All users: `ShellExecuteExW` with `runas`, so Windows asks for UAC before the app quits; for an unsigned release the prompt is expected to say *Unknown publisher* *(⚠ verify, spike W1)*. **No gap between check and run:** the installer is opened with `FILE_SHARE_READ` only (no write or delete sharing, safe Rust through `OpenOptionsExt::share_mode`), the final size, SHA-256 and signature checks run on that handle, and it is kept until the app exits, so other code of the same user can't swap the file after the check. If the lock can't be held, or the installer won't start while it is held (spike W1), a per-user install retries once after another hash check and a per-machine install falls back to *Download* rather than elevating an unlocked file. A declined UAC prompt or a failed start shows *Couldn't start the update* and keeps the app and the offer, so the user can retry. An accepted start returns `Restarting` (a handoff, not proof of success); the app saves its state and quits. The installer waits for the app (REL-024), replaces the files and relaunches it (`/RELAUNCH`; all-users installs relaunch through Explorer, so Dockering never runs elevated). Inno has no atomic rollback: if the installer is cancelled or fails, the next launch of the old version still has the offer (UPD-017) and offers it again. A file written by the app's own HTTP client carries no Mark-of-the-Web, so SmartScreen shouldn't stop it, and Defender or Smart App Control may still block an unsigned app starting an unsigned installer *(⚠ verify, spike W1; a blocked or removed installer makes the offer *Download*)*. Zed-style staged install with a post-exit swap helper MAY come later. |
| UPD-008 | **UI (identical on every platform).** One **title-bar button** (UPD-015) is the persistent sign of an offered update. The status bar shows only transient items: *Downloading update… n%*, and *Checking…* or the error during a manual check. **One notification per version** appears the first time an update becomes actionable: for *Restart to update* when the verified download is ready (*Dockering X.Y.Z is ready to install*, button *Restart now*), for *Download* when the update is found (*Dockering X.Y.Z is available*, button *Download*). Clicking the notification body opens the release notes (a GPUI Kit notification has one action button). `notified_version` is saved in `state.json`, so a restart, an offline start or a restored offer (UPD-017) never repeats the notification; the button is shown from the moment the offer is actionable until it is applied or withdrawn. After an update the first launch shows 'Updated to X.Y.Z' with *What's new* (`notes_url`); that notice is driven only by `last_run_version`, so it shows however the new version was installed (REL-075 and REL-078 rely on it), and clicking *Download* itself changes no state. All URLs open through GPUI `open_url`. |

| UPD-017 | **Retained offer and relaunch** *(implemented 2026-10-20; Linux-verified)*. **The offer mirrors the newest authenticated manifest that is newer than the running version.** It is saved in `offer.json` (UPD-012): the signed manifest bytes and signature, the time of the last successful check (`confirmed_at`), its stage and whether installing it failed. Only *Downloading*, *Ready* and *Installed, restart* are saved; *Applying* exists in memory only. (1) **Restore at start, before any network:** verify the signature against the embedded keys; require the version to be newer than the running one and the platform entry to exist. The title-bar button and Settings show it at once and no second notification appears (UPD-008). (3) **A failed check** (network, HTTP, bad signature, bad manifest) changes nothing. (4) **A successful check:** an entry with the same version, URL and SHA-256 for this platform keeps the stage and the failed-install flag and only refreshes `confirmed_at`; a different entry that is newer than the running version replaces the offer (an install offer after the new payload is verified and its `offer.json` written, UPD-012), and a manifest *lower* than the offer, which is what GitHub's `latest` serves after the offered release is pulled, makes the old offer non-actionable at once and its payload is never applied; **no entry newer than the running version for this platform withdraws the offer and its payload.** (5) The offer is deleted when the running version catches up, after an update or after one done by hand. Without the flag nothing waits, so a desktop launch with stdin on `/dev/null` never blocks. It then starts as a normal launch: after a timeout the single-instance rule (SHL-022) applies, and while it waited it never sent a focus request. The outcome is logged once logging starts. **Frozen from the first updater release** (an old binary starts and tests a new one): the flag and this behaviour (an unknown flag value is ignored), the `--version` output `dockering <semver>` with exit status 0, the `<os>-<arch>` platform keys and the asset names (REL-012). |

  installation, the all-users updater path through `runas`, macOS application launch,

- The `.deb` declares plain `libc6` although its binary needs `GLIBC_2.39`: on Ubuntu 22.04 it installs and then
  fails to start (plan finding F1; REL-073).
- The Apple-silicon `.app` carries a linker signature that does not cover its resources, so Gatekeeper calls a quarantined download "damaged" and offers no *Open Anyway* (plan finding F9; REL-078). The README and the *Unsigned installation* section say otherwise.
- Without a usable Vulkan or GL driver the Linux app logs `failed to open the main window` and keeps running with no window,
  and a second launch starts another such process (plan finding F2). Follow-up in its own plan.
- `PUBLIC_KEYS` in `dk-update/src/keys.rs` is empty until the release keys are generated, so updates fail closed until then (REL-060 checklist).

- The shared updater is implemented but no published build contains it: v0.1.0 to v0.3.0 have no updater, so the first updater build is installed by hand, and a live proof needs a second release after it. In-app installation on macOS is deferred (UPD-016); macOS offers *Download*. Windows installs update without OS signing (UPD-003); an unsigned installer's UAC prompt is expected to say *Unknown publisher* (⚠ verify, spike W1).
- No *Preview* update channel yet (UPD-001 MAY).
- No delta updates. A full installer is about 20–30 MB.
